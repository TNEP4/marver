Marver · Engineering architecture

Hundreds of real web apps on one canvas

The rendering architecture for an infinitely scalable, high-fidelity board — where every node is a genuine live app, not a mockup, and the ceiling is on node count, not on what's live.

Basis · codex deep research (21 web searches) + 6-product teardown Verdict · both converged, no contradictions Status · decision-ready

The answer, in three lines

  • 1
    "Hundreds of simultaneously live web apps" is blocked by browser physics, not effort. Same-origin iframes share one renderer process and one main thread; each costs 10–50 MB and its own compositor layer. No shipping product does it — Figma caps live embeds at exactly one.
  • 2
    The differentiator survives by redefining "real." Every node is genuine repo code with genuine browser layout and state. "Real" describes the authoritative artifact and the focused experience — it does not require every node to execute concurrently. A dormant node is a cached visual materialization of its real app, promoted to live on demand.
  • 3
    The move is to stop N nodes from owning N browser runtimes. A budgeted scheduler lends a live iframe to the tiny working set that earns it; everything else is a crisp raster proxy. That's the whole game — and it scales to hundreds because the ceiling sits on cheap proxies.

01The ceiling is physics

The reason zooming a heavy board flashes white and lags is not a bug we haven't patched hard enough — it's that Chromium re-rasterizes every iframe's content at the zoom scale on each camera tick, and with many iframes it exhausts the GPU tile budget and draws blank tiles. Underneath that sits a harder wall:

The constraint

A normal laptop cannot provide hundreds of independently executing, arbitrarily-scaled browser documents with zero lag. Same-origin iframes cannot be separated onto other threads without severing scripting. This is not tunable.

Two independent references make it concrete: 1000 iframes take Chrome ~3.3s just to instantiate (superlinear beyond that); a decoded 4096×4096 image is ~64 MB regardless of file size, and Chrome's entire decoded-image budget is 128–256 MB. Hundreds of live apps + hundreds of 4K images, all resident, is multiple gigabytes before GPU copies. So the target can't mean "all live at once." It can mean something better.

02What the field actually does

Six product families, researched independently, landed on the identical model: a few live, the rest frozen, seamless promote-on-focus. This is a designed-around constraint, not a v1 shortcut.

Two products define the two lanes. Figma ("DOM doesn't scale — own the pixels with GPU tiles") and tldraw ("DOM is the only way to host live web, and it's fast enough") are both right — they answer different questions. Marver's requirement (live apps) forces the DOM answer for the live layer. GPU tiling can only ever draw the frozen overview.

03The tier model

A board node stops owning a live iframe and a lean iframe for its whole life. The board owns metadata and cached proxy artifacts; a global runtime pool lends a live surface to whichever tiny set earns it. Tiers are chosen from the node's transformed screen rectangle (world size × zoom), with hysteresis so nothing thrashes mid-gesture.

04Deep-zoom fidelity without keeping everything live

"Infinitely crisp" comes from two moves, not from resolution brute force:

1 · A per-proxy mip pyramid

Capture each app snapshot at buckets of 0.25× 0.5× 1× 2× 4×; pick the smallest bucket giving ≥1 source pixel per device pixel; re-raster only after the camera settles and crosses a ~1.4× threshold. High-res images use real tile pyramids (OpenSeadragon / IIIF / DZI — 256–512px tiles, decode only what's visible), never a whole-image <img>.

2 · Promote past 4×

Above 4× (or past texture limits) you stop making enormous screenshots and instead swap the proxy for a DOM snapshot (inspecting) or the live app (focused). Now only one or two documents re-rasterize — so text, SVG and CSS are crisp at any zoom. The deep, detailed view is always the genuine web app.

Honest boundary

DOM text / vectors / CSS stay crisp indefinitely. A photograph cannot exceed its source pixels, and a live app containing a low-res bitmap eventually shows those pixels. That's real, and it's the same boundary Figma and every camera live under.

05Memory & the runtime lifecycle

The scale story is the memory story. Because Marver controls the repo runtime same-origin, it has a real advantage over generic embed products: frames can cooperatively pause. Define a bridge:

interface MarverRuntimeBridge {
  ready()      : Promise<void>
  pause()      : Promise<void>    // quiesce rAF / polling / websockets / media
  resume()     : Promise<void>
  checkpoint() : Promise<unknown> // scroll, route, app state
  restore(cp)  : Promise<void>
}
  • Keep 1 live + 2 warm. Destroy everything else — checkpoint → about:blank → detach listeners → remove element → revoke object URLs → verify memory returns. Never retain contentWindow/contentDocument in long-lived maps (that's the classic detached-window leak).
  • Never reparent a live iframe (destroys state) and never display:none it (throttles + re-lays-out). Park with opacity:.001 in a fixed overlay, or use Node.moveBefore() (Chromium 133+) to move live↔parked without reload.
  • Images: one decode queue, not a swarm. Blob/object URLs (not retained base64), createImageBitmap() → draw → ImageBitmap.close() on eviction, img.decode() before every DOM swap (this alone kills white flashes), srcset to never over-decode.

06Does the high end need a GPU renderer?

For the live layer: no — it's inapplicable. A GPU tile renderer draws bitmaps and structurally cannot host a live React/Next node. "Live app node" and "GPU-tiled node" are mutually exclusive for the same node.

For the cold/overview tier: eventually yes, as an optimization — hundreds of static proxies as one GPU pass sidesteps the "hundreds of forced compositor layers" problem. Build it backend-neutral, WebGL2 first (drawing textured rectangles needs no compute); add WebGPU only when profiling shows a win. It never touches the live tier.

08Staged plan, ranked by impact

  1. highest

    Bound runtime ownership

    Refactor FrameNode so it doesn't permanently mount .sh-live + .sh-lean. Add a global RuntimePool: 1 active + 2 warm + 4 DOM-proxy slots, with priority scheduling and memory-pressure eviction. Culling becomes proxy mount/decode, not iframe suspension. This is the change that unlocks hundreds.

  2. high

    Make raster the permanent passive representation

    Promote the motion-only raster coordinator to canonical: versioned buckets, Blob URLs, freshness keys, visible-first + predicted-direction prefetch, and "proxy never disappears until its replacement has decoded."

  3. high

    Live screen-space portal + pause/checkpoint bridge

    Move the active iframe out of the scaled world into an untransformed overlay. Implement MarverRuntimeBridge. Targets: warm→live <150ms p50, cold→interactive <500–800ms p95, zero exposed blank frames.

  4. medium

    Multiresolution artifacts + image tile pyramids

    0.25×–4× app buckets; DZI/IIIF tiles for uploaded images (decode only visible tiles, keep the coarse parent until children decode → no flash). Optionally pre-generate artifacts out-of-band via the project's real Chromium (Playwright), keyed by revision + route + viewport + theme + state-hash.

  5. medium

    Bound the DOM snapshot tier

    Keep the lean snapshot for the selected/largest settled node and pre-live deep zoom only. Never one lean iframe per node.

  6. later

    Add the GPU proxy plane

    WebGL2 quad/tile renderer for the cold tier + image tiles; DOM keeps chrome/selection/live-portal; <img> fallback on context loss.

  7. continuous

    Release gates on real boards

    Test 500 app nodes + 500 4K images; 100+ visible proxies; fit-all→one-frame zoom; focus-cycle 20 heavy apps; 1-hour memory plateau. Gate: no blank frames, camera p95 <20ms, no >50ms gesture long-tasks, runtime count ≤ capacity, cache returns below watermark after nav.

09Recommendation

Adopt the tiered K-live + proxy model and treat Stage 1 (bound runtime ownership) as the next real milestone — it's the one change that converts "optimize N iframes harder" into "N nodes never own N runtimes," which is what makes the AI-content ceiling a non-issue: the ceiling is on cheap proxies, not on live apps.

Before committing the full refactor, the highest-value next step is a one-day validation spike: DOM canvas, 200 nodes, an 8-slot live pool with LRU promote/demote over foreignObject proxies, measured on a MacBook Air. That converts the industry's numbers into Marver's numbers and de-risks the RuntimePool design before it's load-bearing.

The honest ceiling — and why it's fine

"Hundreds of apps, all interactive, all at once, zero lag" is not achievable on one same-origin main thread. "Hundreds of nodes, a handful live at a time, the rest crisp proxies with seamless promote-on-focus" is. And because AI drives up node count (cheap proxies) rather than live count, the architecture scales exactly where the pressure comes from. Every node stays a real web app; only the working set executes.
